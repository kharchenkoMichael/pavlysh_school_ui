`python -m app.seeds.create_user --username ...`. Проксі на Azure SWA
не робимо: логін працює будь-де, не лише там, і не потребує налаштувань
у порталі.

Токен лежить у `sessionStorage`: переживає перезавантаження сторінки
(розрахунок триває хвилини, і губити його через випадковий F5 не можна),
але не лишається у браузері після закриття вкладки.

**Перевірено:** обидві збірки (`development` і `production`) проходять;
у зібраному бандлі немає ні ключа, ні згадки `X-API-Key`; адмінських
компонентів у `main.js` немає — усе лінивими чанками. Живий бекенд
відповідає на ті самі шляхи, якими ходить адмінка, і CORS пропускає
заголовок `Authorization`.

**Не перевірено:** ніхто ще не клікав по цих сторінках у браузері.
Збірка ловить помилки шаблонів і типів, але не логіку взаємодії.
Це перше, що варто зробити далі:

```
cd ..\pavlysh-school-api
.venv\Scripts\python -m uvicorn app.main:app --reload   # :8000
cd ..\pavlysh_school_ui
```

## 2. 🔴 Вирішити ДО написання коду: ключ адміністратора

**Проблема.** Авторизація API — `X-API-Key`, звірений із одним
`settings.admin_api_key` (`app/dependencies/security.py`). Це спільний секрет.
**SPA не вміє тримати секрети:** усе, що потрапляє в Angular-бандл, віддається
браузеру. На публічному сайті ключ можна витягти з `main.js` і отримати повний
доступ до API школи — не лише до розкладу, а й до новин та працівників.

Репозиторій публічний і автоматично викочується в Azure Static Web Apps на
кожен пуш у `dev` (`.github/workflows/`). Тобто «ми потім приберемо» не працює.

**Уточнення.** Сам ключ зберігається в налаштуваннях Azure, а не в коді
бекенда — це правильно й це вже зроблено. Діра не там. Проблема в тому, що
браузер ходить на API **напряму за повною адресою**
(`pavlysh-school-api-...azurewebsites.net`), тож заголовок `X-API-Key`
мусив би формувати сам фронтенд — а отже знати ключ.

**Варіанти, від найкращого:**

| # | Рішення | Плюси | Мінуси |
|---|---|---|---|
| **A** | **Проксі на Azure SWA.** Керована функція в теці `/api` живе на сервері, читає ключ із налаштувань SWA і сама переадресовує запит на FastAPI. Браузер ходить на `/api/...` свого ж домену **без ключа**. Зверху — `staticwebapp.config.json` з `allowedRoles` на ці маршрути | Секрет лишається в Azure й ніколи не потрапляє в бандл; бекенд **не чіпаємо взагалі**; авторизація сторінки й API — одним механізмом | Треба написати тонку функцію-проксі й налаштувати провайдера входу |
| B | **Справжній логін в API** — `/auth/login` видає JWT з коротким TTL | Працює будь-де, не лише на Azure; можна ролі | Треба дописати ендпоінти й таблицю користувачів на бекенді |
| C | **Адмінку не деплоїти** — `ng serve` локально, ключ у `environment.development.ts` з `.gitignore` | Найшвидше | Завуч не зайде зі свого комп'ютера |

**Рекомендація: A.** Вона найкраще лягає на те, що вже є: ключ уже в Azure,
залишити його там і просто не пускати браузер до нього. Бекенд лишається
недоторканим — жодних змін у `security.py`.

**Що конкретно зробити для A:**

- [ ] Тека `/api` в корені UI-репозиторію — керовані функції SWA
- [ ] Функція-проксі: приймає `/api/{*path}`, додає `X-API-Key` з
      `process.env.ADMIN_API_KEY`, переадресовує на FastAPI, повертає відповідь
- [ ] `ADMIN_API_KEY` — в Application settings статичного вебзастосунку
      (портал Azure), **не** в репозиторії
- [ ] `staticwebapp.config.json`: `allowedRoles` на `/rozklad/*` і `/api/*`
- [ ] Провайдер входу (Microsoft/GitHub) + призначення ролі завучу
- [ ] Перевірити, що `apiUrl` адмінських сервісів вказує на `/api`,

**Перевірка, що зроблено правильно:** зібрати production-бандл і пошукати
в ньому ключ — `grep -r "<фрагмент ключа>" dist/`. Має не знайтися нічого.

**Чого не робити ніколи:** не класти ключ у `environment.prod.ts`, не
«ховати» його за base64 і не тримати в localStorage після введення в поле.
Останнє гірше за все: ключ вічний, а localStorage читається будь-яким
скриптом на сторінці.

## 4. Конвенції цього репозиторію

Дотримуватися, а не вигадувати своє.

- **Angular 18.2, standalone-компоненти.** Ніяких NgModule
- `provideHttpClient()` підключено в `src/main.ts`, не в `app.config.ts`
- Роути — у `src/app/app.routes.ts`, з `data: { title, description }`
- Структура: `pages/<назва>/` для сторінок, `shared/components/` для спільного,
  `services/`, `models/`
- Стилі — SCSS, змінні в `src/assets/styles/variables.scss`
- Кожен компонент — три файли: `.ts`, `.html`, `.scss`

**Одна зміна конвенції — свідома.** Наявні роути імпортуються жадібно вгорі
`app.routes.ts`, тобто все лежить у головному бандлі. Адмінку так робити не
можна: вона роздує бандл публічного сайту й потрапить у нього повністю.
Використати **ліниве завантаження**:

```ts
{
  path: 'rozklad',
  loadChildren: () => import('./admin/rozklad.routes').then(m => m.rozkladRoutes),
  canActivate: [adminGuard],
}
```

Це не робить код секретним — лінивий чанк усе одно можна завантажити вручну.
Але він не потрапляє в бандл, який отримує кожен відвідувач сайту.

## 6. Екрани

### 6.1. Довідники — вчителі, класи, кабінети, предмети

Найпростіші. Таблиця + форма. Один спільний компонент `dovidnyk-table`
з конфігурацією колонок замість чотирьох майже однакових.

**Обов'язково:** перед видаленням запитати бекенд `/zvyazky` і показати,
де запис використовується. Бекенд поверне 409 зі списком — не ковтати його,
а показати людині: «Ковальова Л. М. веде 18 годин у 4 класах. Видалити
все одно?». Мовчазне видалення тихо ламає дані.

**Пастка на прізвищах.** У школі три Сірі — Альбіна Віталіївна, Наталія
Іванівна і Наталія Олександрівна; дві останні різняться лише по батькові.
Ще дві Шевченко, дві Марченко, двоє Скориків, дві Ірини в адміністрації.
**Ніде не показувати лише прізвище** — завжди з ініціалами.

### 6.2. Класи

Крім назви: кількість учнів, паралель, зміна (або «підбере програма»),
скільки уроків витримує клас.

Кількість учнів — не формальність: саме вона рахується проти місткості
укриття. Показувати підсумок зверху: «22 класи, 498 учнів, укриття 300 —
мінімум для однієї зміни 198».

### 6.3. Навантаження — головний екран введення

Матриця **клас × предмет**, у клітинці — години й учитель. Це те, що завуч
заповнює довго, тож тут вирішує зручність:

- заповнення з клавіатури без миші, перехід Tab/Enter;
- копіювання рядка в паралельний клас (5-А → 5-Б);
- підсумки по рядку (годин у класі) і по стовпчику (годин у вчителя) —
  одразу видно перебір чи недобір;
- підсвічування, якщо в учителя виходить понад 24 години;
- **поділ на підгрупи** — галочка й другий учитель. Якщо вчителі різні,
  підгрупи йдуть одночасно у двох кабінетах; якщо один — розійдуться на різні
  уроки. Це треба написати підказкою прямо в інтерфейсі, інакше незрозуміло.

### 6.4. Правила — те, заради чого показуємо завучу

Зроблено. Три купки замість одного списку — бо перше питання завуча
саме таке: **що тут виконується залізно, а що можна посунути**.

- **Виконується залізно** — програма не має права порушити;
- **Побажання зі штрафом** — відсортовані за вагою, у кожного видно ціну
  порушення прямо в заголовку;
- **Вимкнені**.

У кожного правила:

- перемикач **залізно / зі штрафом / вимкнено**;
- повзунок ціни порушення (1–10);
- параметри (до якого уроку, скільки поспіль, для яких предметів);
- **пояснення людською мовою з посиланням на джерело** — воно приходить
  із бекенда разом із каталогом, тож додане в солвері правило описувати
  вдруге не треба;
- «повернути як було» — значення з каталогу солвера.

Якщо солвер уміє правило, якого в довіднику школи ще немає, сторінка
сама це помічає й пропонує додати. Так нове правило доїжджає до завуча
без міграцій і без «зайдіть до розробника».

Приклад того, як має виглядати пояснення:

> **Складні предмети — у першій половині дня**
> Найвища працездатність — на 2–4 уроках. Санітарний регламент (наказ МОЗ
> №2205) рекомендує ставити предмети, що потребують значного розумового
> напруження, саме туди.

Це не прикраса: завуч має бачити, що правила не вигадані, а взяті з норм.

Каталог правил і ваги за замовчуванням — у плані бекенду, розділ 7.

### 6.5. Запуск

- ліміт часу (за замовчуванням 120 с);
- режим: **скласти з нуля** / **оцінити наявний** / **покращити наявний**;
- для покращення — «наскільки триматися наявного» повзунком;
- завантаження CSV торішнього розкладу;
- індикатор процесу: розрахунок триває хвилини, тож потрібне опитування
  статусу раз на 2–3 секунди й чесний напис «рахую», а не застиглий екран.

**Формат CSV:** `klas,den,urok,predmet,vchytel,zmina,hrupa`.
Показати зразок для завантаження. Якщо частина рядків не зіставилася —
**показати які**, а не мовчки оцінити по половині даних.

### 6.6. Результат

- таблиця по кожному класу: уроки × дні;
- поділ по змінах із запасом місткості укриття;
- **«чим довелося пожертвувати»** — які побажання порушено й наскільки;
- для режиму покращення — **«що саме зрушилося»**: скільки уроків лишилося
  на місці, скільки переставлено і які саме;
- вигляд «по вчителю» — окремо, бо саме там видно вікна;
- друк і експорт у CSV.

Головне число на екрані — **кількість вікон у вчителів**. Воно найзрозуміліше
й найпереконливіше.

## 8. Граблі

**8.1. Розрахунок триває хвилини.** Не тримати HTTP-запит відкритим.
Бекенд віддає id одразу, статус опитується окремо. Якщо користувач
перезавантажить сторінку — не втратити id, тримати його в URL.

**8.2. Публічний бандл.** Не класти в репозиторій жодних даних: ні прізвищ
у моках, ні `shkola.yaml`, ні ключів. Для розробки — синтетичні дані
з вигаданими прізвищами.

**8.2а. Ключ не має потрапити в бандл навіть випадково.** Найлегше
помилитися так: покласти `adminApiKey` в `environment.ts` «тимчасово, поки
не налаштуємо проксі». Воно поїде в Azure з першим же пушем у `dev`, бо
деплой автоматичний. Після кожної зміни авторизації — перевіряти
`grep` по `dist/`.

**8.3. Дублювання адреси API.** Не копіювати рядок з `employee.service.ts`
у нові сервіси. Спершу винести в environments.

**8.4. Жадібні імпорти в `app.routes.ts`.** Не додавати адмінські компоненти
туди — тільки `loadChildren`.

**8.5. Однакові прізвища.** Скрізь із ініціалами. Три Сірі — реальна пастка,
дві з них Наталії.

**8.6. Кількість учнів — не декорація.** Від неї залежить поділ на зміни.
Порожнє поле = 0 учнів = розклад, який пройде перевірку укриття й буде
неправильним. Валідувати.

## 9. Відкриті питання

- Чи має завуч бачити чужі персональні дані вчителів, чи лише ПІБ і предмети?
- Чи потрібні ролі (директор бачить усе, завуч редагує, вчитель дивиться свій
  розклад), чи достатньо одного адміністратора?
- Чи публікувати готовий розклад на публічній частині сайту для учнів —
  і якщо так, то це вже інший, простий екран без авторизації.
